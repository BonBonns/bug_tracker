# ESCAPE-PARITY-BOUNDARY — Source Mode Filter (R08)

`reportable=false` — no finding generated by this revision is submitted.

## Problem

The C/C++ reachability producer models `fopen` as a `STORED_FILE_READ` delayed source by
matching on the function name alone.  It does not inspect the mode argument.

A hand scan of the gecko-dev prefix snapshot candidate
(`MimeType::SplitMimetype`, `dom/base/MimeType.cpp`) reveals that the two
"resolved sources" the chain reported were:

| File | Line | Call | Mode | Purpose |
|---|---|---|---|---|
| `dom/base/nsDOMWindowUtils.cpp` | 4649 | `fopen(filename.str().c_str(), "wb")` | write-only | writes frame PNG in `WriteRecordingToDisk` |
| `dom/base/nsGlobalWindowInner.cpp` | 991 | `fopen(fname.get(), "wb+")` | write+read | opens dump output file in window constructor |

Both open files for **writing**, not reading.  The returned `FILE*` is used only for
`fwrite` / `fputs` / `Dump()` in their respective subsystems, never for reading content
that flows to a text parser.  Neither call is topologically reachable from
`SplitMimetype`.

R07 reported:
```
"search_space": {
  "resolved_sources_in_unit": 2,
  ...
  "flow_edges_in_unit": 0
}
```
and reason `NO_DELAYED_SOURCE_REACHES_PARSER`.

This is _technically_ a traced negative: the flow engine ran 2 source→parser queries
(one per resolved source × one parser call site) and returned 0 paths.  But the source
count is wrong: write-mode `fopen` calls cannot supply read data to a text parser, so
they should not inflate `resolved_sources_in_unit`.  The correct answer is
`resolved_sources_in_unit = 0`, which would change the reason to `NO_SOURCE_API_MODELLED_IN_UNIT` —
the vacuous form — which is accurate: the model does not have a read source in the
`MimeType.cpp` analysis unit.

The distinction matters.  `NO_DELAYED_SOURCE_REACHES_PARSER` implies "we traced this
and found no path"; `NO_SOURCE_API_MODELLED_IN_UNIT` implies "the unit has no source
the model recognises".  Only the second is honest when the only fopen calls are opens
for writing.

## Fix

### `producers/cpp_reachability_facts.sc`

For `fopen` specifically, extract the mode argument (argument position 2 in the
1-based c2cpg scheme).  Classify by mode:

| Mode pattern | Readable? | Resolution |
|---|---|---|
| literal containing `r` or `+` | yes | `RESOLVED_EXTERNAL` / `AMBIGUOUS_LOCAL_DEFINITION` |
| literal starting with `w`/`a`, no `+` | no | `WRITE_ONLY_MODE_EXCLUDED` — row suppressed |
| non-literal (variable) | unknown | `AMBIGUOUS_MODE_ARGUMENT` — row kept, flagged |

`WRITE_ONLY_MODE_EXCLUDED` rows are dropped entirely (not emitted to `delayed_sources.tsv`)
so they neither inflate `resolved_sources_in_unit` nor appear as abstentions.

### `escape_parity_chain.py`

Add `flow_edges_by_kind` to every candidate chain's `search_space`:

```json
"flow_edges_by_kind": {
  "DELAYED_SOURCE2PARSER": 0,
  "PARSER2CONSUMER": 0,
  "PARSER2ENCODE": 0,
  ...
}
```

The aggregate `flow_edges_in_unit` cannot distinguish a unit where
`DELAYED_SOURCE2PARSER` ran and returned empty from one where it was never attempted.
Per-segment counts let a reader independently verify which chain segment failed and
whether its flow query produced any edges at all.
