# Frontend entrypoint-coverage correction: a standalone tool for the `JOERN_PARSING_GAP` finding

This closes the open item flagged in `R02_DECISION.md` ("A third, real finding this taxonomy has
no slot for") and root-caused in `REMAINING_SIX_NO_COMPLEXITY_CANDIDATE.md` section 4: jssrc2cpg's
own default folder-ignore list drops `dist/` unconditionally, and for a package whose
`package.json` entrypoints resolve *entirely* into `dist/` with no parallel `src/` shipped
(`multi-spec-parser@0.4.2` is the real, confirmed instance), the real CPG never contains a single
node for the package's real code. The frozen producer then correctly reports zero sinks over the
CPG it was handed -- a false "nothing to find," not a real negative.

**This is a standalone tool, not a pipeline change.** It does not touch
`export_redos_npm_integ.sc`, `export_redos_npm_integ_r02.sc`, `redos_verdict.py`,
`provenance.py`, `staged_enablement.py`, or any pipeline-wiring file. It runs before/alongside a
real `jssrc2cpg.sh` build and reports a distinct, itemized coverage verdict.

- Tool: `pilot25/audit/frontend_coverage_check.py`
- Fixtures: `study/redos_npm/frontend_coverage_fixtures/` (5 small packages: 3 pure
  `package.json`-parsing shapes, 1 multi-spec-parser-style dist-only synthetic package, 1
  src+vendored-dist discipline-check package)
- Helper Joern script written at first use (not committed source, generated by the tool itself):
  `pilot25/audit/_fcc_list_cpg_files.sc`

## 1. The real override-mechanism question: no CLI flag exists

`jssrc2cpg.sh --help`, run directly against the installed
`$JOERN_HOME/frontends/jssrc2cpg/lib/io.joern.jssrc2cpg-4.0.608.jar`:

```
Usage: jssrc2cpg [options] input-dir

  input-dir                source directory
  -o, --output <value>     output filename
  --exclude <file1>        files or folders to exclude during CPG generation (paths relative to <input-dir> or absolute paths)
  --exclude-regex <value>  a regex specifying files to exclude during CPG generation (paths relative to <input-dir> are matched)
  --enable-early-schema-checking
                           enables early schema validation during AST creation (disabled by default)
  --enable-file-content    add the raw source code to the content field of FILE nodes to allow for method source retrieval via offset fields (disabled by default)
  --help                   display this help message
```

**`--exclude`/`--exclude-regex` only ever ADD more exclusions on top of the defaults -- there is no
flag to disable, override, or narrow the default ignore-folder list, the default ignore-suffix
regex, or the line-length minified-file cutoff.** Confirmed a second, independent way: the jar was
re-decompiled for this task (`javap -p -c` and `strings` against
`io.joern.jssrc2cpg.utils.AstGenRunner$.class`, the same class `PREFILTER_DIVERGENCE_AUDIT.md`
decompiled). The folder-name ignore list is embedded as a fixed constant array baked into that
class's static initializer (`node_modules, venv, docs, test, tests, e2e-beta, examples, cypress,
jest-cache, eslint-rules, codemods, flow-typed, i18n, vendor, dist, build`, matching
`PREFILTER_DIVERGENCE_AUDIT.md`'s own documented list), never read from any CLI option, config
file, or environment variable. **Remediation path (a) from `R02_DECISION.md` -- "check whether
jssrc2cpg.sh exposes an ignore-list override flag" -- is confirmed negative: it does not.**

So this tool implements remediation path (b): a pipeline-level pre-processing step that stages a
corrected copy of the source tree before the real `jssrc2cpg.sh` build.

## 2. How the tool works

1. **Entrypoint resolution** (`resolve_entrypoints`): reads `main`, `module`, `types`/`typings`,
   and every string leaf inside `exports` (handling both a plain string and a nested
   conditional-exports map/object, recursively), falling back to `./index.js` when no entrypoint
   field exists at all. Verified against three real fixture `package.json` files:
   - `frontend_coverage_fixtures/plain_main/package/package.json` (`"main": "./index.js"`) ->
     resolves to `['index.js']`
   - `frontend_coverage_fixtures/nested_exports/package/package.json` (nested `"exports"` with
     `"."` -> `{import, require}` and `"./sub"` -> a plain string) -> resolves to
     `['dist/sub.js', 'dist/x.cjs', 'dist/x.mjs']`
   - `frontend_coverage_fixtures/no_entrypoint_field/package/package.json` (no `main`/`exports` at
     all) -> resolves to `['index.js']` (Node's own default)
2. **First-pass real CPG build + inspection**: runs the real `jssrc2cpg.sh -o <cpg> <src_dir>`
   (same invocation pattern as `run_pilot25.py`), then a real Joern query
   (`cpg.file.name.l`, run via `joern --script`) to list every file the CPG actually contains --
   the same mechanism `REMAINING_SIX_NO_COMPLEXITY_CANDIDATE.md`'s own "FILES IN CPG" listings
   used (confirmed by finding and reusing that investigation's own scratch `query3.sc`, itself
   `importCpg(cpgFile); cpg.file.name.l.sorted.foreach(...)`). Verified directly against a fresh
   synthetic probe CPG before being trusted: a file placed under a `dist/` subfolder was
   confirmed absent from `cpg.file.name.l`, while a sibling top-level file was present.
3. **Coverage cross-reference**: each resolved entrypoint's declared path (`./dist/src/index.js`)
   is normalized to the CPG's own path namespace (`package/dist/src/index.js` -- confirmed by
   direct comparison against the probe CPG's real output, not assumed) via
   `os.path.relpath(entrypoint_abspath, jssrc2cpg_input_dir)`, then checked against the file set.
4. **Entrypoint-identity-driven recovery**: for every entrypoint missing because of a real
   jssrc2cpg default-ignore rule (reusing the exact same constants documented in
   `PREFILTER_DIVERGENCE_AUDIT.md`, re-confirmed against the jar above -- never invented), the
   tool stages a *copy* of the source tree and, ONLY for the specific ignored ancestor
   directory/file that is part of a *missing, resolved* entrypoint's own path, relocates it:
   - `FOLDER_IGNORE`/`NODE_MODULES` (e.g. the whole `dist/` ancestor directory): renamed in place
     to `_redos_included_<foldername>` -- moving the whole directory as a unit, so internal
     relative imports between files under it (`dist/src/index.js` importing
     `dist/src/spec-validation.js`) stay valid.
   - `SUFFIX_IGNORE` (e.g. `index.d.ts`, matching jssrc2cpg's `(conf|test|spec|[.-]min|\.d)\.(ext)$`
     suffix rule): the offending file is copied to a sibling name with `_redosinc` inserted
     immediately before the final extension (`index.d.ts` -> `index.d_redosinc.ts`), which
     structurally cannot re-match that suffix regex in any case, applied *after* any folder-level
     rename so a file whose ancestor also got moved is copied from its current (post-rename)
     location, not a stale path.
   A second, real CPG is then built from the staged copy and re-inspected the same way.
5. **Exclusion accounting**: independent of the CPG, every real `.js`/`.ts`/`.mjs`/`.cjs` file
   found by a raw, unfiltered walk of the extracted tarball is classified against the same
   ignore-rule constants (`NODE_MODULES` / `SUFFIX_IGNORE` / `FOLDER_IGNORE` /
   `LINE_LENGTH_MINIFIED`), with up to 10 example paths per reason, reported alongside the CPG
   counts (`n_raw_js_ts_files`, `n_files_in_first_pass_cpg`, `n_files_in_corrected_cpg`).
6. **Terminal statuses**, each written into `status`, never conflated:
   - `OK_ALL_ENTRYPOINTS_COVERED` -- no correction needed, all resolved entrypoints were already in
     the first-pass CPG.
   - `OK_RECOVERED_ALL_ENTRYPOINTS` -- correction was needed and succeeded for every missing
     entrypoint.
   - `ENTRYPOINT_NOT_PRESENT_IN_CPG` -- one or more real, resolved entrypoints still could not be
     gotten into the CPG after the correction attempt; the result carries the exact entrypoint
     path(s) and reason(s). This is a distinct signal from "zero sinks found" for a future
     consumer of this tool's JSON output.
   - `CPG_BUILD_FAILED` / `CORRECTED_CPG_BUILD_FAILED` / `NO_PACKAGE_JSON` for infrastructure
     failures.

## 4. Discipline check (item 6): ordinary vendored `dist/` stays excluded

The core risk of this whole approach is un-ignoring folders indiscriminately. The tool is built to
be entrypoint-identity-driven: it only ever relocates the specific ignored ancestor of a
*missing, resolved* entrypoint, never every occurrence of an ignored folder name. Verified two
ways:

**Synthetic fixture** (`frontend_coverage_fixtures/src_plus_vendored_dist/`): `package.json`
declares `"main": "./src/index.js"` (a real, non-ignored `src/`), and the package separately ships
`dist/vendored-bundle.js` -- a genuinely vendored build artifact containing its own
dangerous-shaped regex, deliberately, so a wrongful recovery would be directly observable in the
producer's counts. Real run:
```
status: OK_ALL_ENTRYPOINTS_COVERED
correction_applied: false
frozen_producer_summary: {"sink_targets": 1, "dangerous_sinks": 0, ...}
```
`dist/` was never touched (`correction_applied: false` -- the tool never even attempted a staging
copy, because the one resolved entrypoint, `src/index.js`, was already present in the first-pass
CPG), and the frozen producer's real, unmodified rerun confirms `dangerous_sinks: 0` -- the
dangerous pattern planted inside the vendored `dist/vendored-bundle.js` was never seen, exactly as
it should be.

**Real pilot package**: `linux-device@2.1.4` (`package.json`: `"main": "index.js"`; the package
also ships a vendored Google Code Prettify library under `docs/scripts/prettify/`, the same real
package `PREFILTER_DIVERGENCE_AUDIT.md` documented as `docs`-folder-excluded, unrelated to its
entrypoint -- fetched fresh from `https://registry.npmjs.org/linux-device/-/linux-device-2.1.4.tgz`).
Real run:
```
n_raw_js_ts_files: 12
static_exclusion_accounting.counts: {FOLDER_IGNORE: 4, SUFFIX_IGNORE: 1, NODE_MODULES: 0, LINE_LENGTH_MINIFIED: 0}
  FOLDER_IGNORE examples: package/docs/scripts/linenumber.js, package/docs/scripts/prettify/lang-css.js,
                          package/docs/scripts/prettify/prettify.js, package/test/testAPA102.js
n_files_in_first_pass_cpg: 7
entrypoint_coverage_first_pass["index.js"]: present_in_first_pass_cpg = true
status: OK_ALL_ENTRYPOINTS_COVERED
correction_applied: false
```
`index.js` was already covered, so no staging happened at all; the real vendored `docs/` content
(and `test/`) stayed excluded exactly as jssrc2cpg's default rule intends, and the tool correctly
did nothing to it. **Discipline check passed on both a synthetic and a real package: the fix is
entrypoint-identity-driven, not a blanket "always include dist/".**

## 5. Output contract for a future pipeline integration

Per-package JSON result includes (not wired into any aggregator here):
`package_name`, `package_version`, `resolved_entrypoints_declared`, `n_raw_js_ts_files`,
`static_exclusion_accounting` (itemized counts + examples per reason),
`n_files_in_first_pass_cpg`, `entrypoint_coverage_first_pass` (per-entrypoint present/reason/
recovered-path), `correction_applied`, `recovered_path_map`, `n_files_in_corrected_cpg`
(when correction was attempted), and a `status` in
`{OK_ALL_ENTRYPOINTS_COVERED, OK_RECOVERED_ALL_ENTRYPOINTS, ENTRYPOINT_NOT_PRESENT_IN_CPG,
CPG_BUILD_FAILED, CORRECTED_CPG_BUILD_FAILED, NO_PACKAGE_JSON}` -- with
`ENTRYPOINT_NOT_PRESENT_IN_CPG` always distinct from "scanned, zero sinks," carrying the specific
entrypoint path(s) and reason(s) it could not resolve, so a future aggregator can abstain
correctly instead of silently recording a false negative.

## 6. Scope notes

- This tool changes nothing about which patterns get classified `DANGEROUS`/`SAFE`/`UNKNOWN`
  (`classifyPattern`/`classify_dangerous` are untouched) and nothing about Stage 1 pattern
  resolution (`resolvePattern` is untouched) -- it only changes what source jssrc2cpg is given to
  build a CPG from, and only for the exact ignored files that are a real, declared package
  entrypoint.
- Not wired into `redos_verdict.py`, `provenance.py`, `staged_enablement.py`, or any aggregator, as
  directed. `export_redos_npm_integ.sc` and `export_redos_npm_integ_r02.sc` are both untouched;
  this task's real producer reruns used the frozen file exactly as `run_pilot25.py` invokes it.
